# 场景二：组织共享知识库

## 场景定义

知识库存在的目的是为了把个人掌握的信息作为"上下文"共享给上下游。知识库不是给自己看的，而是给协作者看的——让下游能快速理解你的判断依据、决策逻辑和历史经验。

典型用户：企业中的决策层、产品经理、研发工程师、销售经理等。

关键区分：知识应该是别处找不到的、有决策价值的个人经验。但通用知识（术语、规则、标准、方法论）也应该进入 wiki，只是必须与上下文知识（案例、项目报告、过程讨论）形成双向关联——因为脱离了具体案例的规则定义没有说服力，脱离了规则归纳的案例则无法复用。

## 访谈流程

场景二的核心是搞清楚**你的知识服务谁、你们的协作关系是什么、你的输入输出是什么。**

访谈按以下顺序展开，每组问题问完后简要复述用户回答，确认理解再继续下一组。

### 第一步：受众与目的

提问：
1. 你当下这个知识库是要给谁看的？
2. 你为什么要给这些人看？他们看了之后应该能做什么？

访谈目的：确定受众和目标，直接影响 AGENTS.md 角色定义和写作风格。

追问方向：如果用户说"给团队看"，继续追问具体角色——"团队里是产品经理看、还是销售看、还是老板看？"不同角色关注的信息粒度不一样，写法也不一样。

### 第二步：协作关系现状

提问：
1. 你之前跟这些人的协作关系是什么？
2. 你们日常怎么交互的？（开会、邮件、文档、口头……）
3. 交互中有没有让你觉得重复或低效的环节？

访谈目的：挖掘现状中的信息流和痛点。痛点往往就是知识库最该解决的问题——比如"每次都要从头解释一遍"说明解释逻辑应该沉淀，"审核标准不透明"说明规则需要文档化。

### 第三步：业务协作的输入输出（现状）

这里的"输入输出"指的是在没有这个知识库的时候，用户与受众之间的日常协作信息流。理解这个现状，才能知道哪些信息值得被沉淀。

提问：
1. 你的受众日常会给你提交什么东西？（需求单、样品、数据、问题……）
2. 你收到之后需要做什么？（审核、确认、分析、批复……）
3. 你日常需要向受众传递或解释什么东西？（可行性判断、评审结论、培训内容……）
4. 每次解释或审核时，你依赖的判断依据是什么？

访谈目的：揭示哪些日常协作信息值得被沉淀为 wiki 内容。

追问方向：
- "每次解释口味可行性，你都要从头说一遍吗？" → 如果是，这个解释逻辑就应该沉淀
- "受众提交的东西，你审核时看哪些维度？" → 这些维度就是规则
- "有没有审核不通过的情况？不通过的原因是什么？" → 坏案例的素材

### 第四步：知识库的输入输出（目标）

这里的"输入输出"指的是有了这个知识库之后，用户计划往 wiki 里放什么、产出什么。这一步应基于第三步的真实信息流来引导，而不是让用户凭空想象。

提问：
1. 基于刚才聊的日常协作，你觉得哪些信息应该沉淀到知识库里？
2. 知识库建好之后，你希望受众看知识库时能直接获取什么？
3. 你预计后续会持续往知识库里添加什么类型的内容？

访谈目的：定义知识库的内容边界和产出目标。

如果用户给出空泛的回答（比如"把所有有用的都放进去"），用第三步的具体场景拉回来："你刚才说每次审核都依赖口味评估标准，那这个评估标准是不是应该先放进去？"

### 第五步：规则与审核

提问：
1. 你的输入和输出的规则是什么？（什么样的需求算合格？什么样的结论算通过？）
2. 你们是如何审核这些规则的？规则是固定的还是会变化？
3. 这些规则有没有文档化的版本？还是都在你脑子里？

访谈目的：确定 `concepts/` 中的规则定义和标准。

规则的文档化程度直接影响知识库的初始工作量。如果规则已文档化，可以直接导入；如果都在脑子里，需要通过访谈逐步提取——这时候第六步的案例就特别重要，因为案例是提取隐性规则的最佳素材。

### 第六步：内容种子

提问：
1. 能不能给我一个好的规则案例？（规则被正确执行、带来好结果的情况）
2. 能不能给我一个坏的规则案例？（规则没被执行、或规则本身有问题、导致坏结果的情况）
3. 坏案例当时造成了什么后果？
4. 能不能给我一个完整的项目介绍？（从输入到输出到结果的全过程）

访谈目的：拿到真实的内容种子。好案例和坏案例进入 `cases/`，引用的规则进入 `concepts/`。

好案例和坏案例的价值不同：好案例示范"应该怎么做"，坏案例揭示"为什么不能这样做"。两者都需要，因为受众不仅需要学习正确路径，还需要理解错误路径的后果。

## 边界情况处理

| 情况 | 处理方式 |
|------|---------|
| 用户说"给所有人看" | 追问"最核心的读者是谁"，按核心读者定写作风格 |
| 用户说"规则都在脑子里" | 重点从第六步的案例中反向提取规则，而非直接问规则 |
| 用户拿不出案例 | 问"最近一次开会解释了什么"，会议内容也是案例素材 |
| 用户说"我想把所有东西都放进去" | 用第三步的具体信息流引导："先放你最常重复解释的那个" |
| 用户同时有外部资料和个人经验 | 外部资料进 `wiki/sources/`，个人经验进 `cases/`，两者通过 `concepts/` 关联 |

## 翻译规则

### 访谈结果 → 目录结构

| 访谈维度 | 映射到目录 | 说明 |
|---------|-----------|------|
| 业务输出中的判断依据 | `wiki/concepts/` | 评估方法、审核标准 → 概念/规则页 |
| 业务输出中的具体案例 | `wiki/cases/` | 好案例、坏案例、完整项目 → 案例页 |
| 受众期望获取的成品 | `wiki/outputs/` | 规范文档、决策支撑 → 输出页 |
| 协作中的过程讨论 | `raw/` 下对应子目录 | 会议纪要、审核记录等原始材料 |
| 受众提交的输入处理 | `wiki/cases/` | 审核过程和结论作为案例记录 |
| 个人思考与反思 | `wiki/thoughts/` | 对规则的改进思考、对协作的反思 |
| 外部参考资料 | `wiki/sources/` | 行业标准、外部报告的摘要（如有） |

场景二通常不需要 `entities/`、`products/`、`synthesis/`，但 `concepts/` 和 `cases/` 是必须的。如果用户同时有外部资料摄入需求，保留 `sources/`。

### 访谈结果 → AGENTS.md 工作流

| 访谈维度 | 映射到工作流 |
|---------|------------|
| 受众与目的 | AGENTS.md 角色定义 |
| 协作痛点 | 工作流中的解决目标 |
| 业务输入处理 | "审核记录沉淀"工作流 |
| 业务输出 | "输出沉淀"工作流 |
| 规则审核方式 | "规则更新"工作流 |
| 内容种子 | "首次内容处理"流程 |
